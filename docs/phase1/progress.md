## Known issues

- **One Dagster at a time against dev BigQuery.** Each instance keeps its own state, so two would both parse every new capture, and a parse appends without a lock: two runs close together load the same file twice. The same goes for `jtf parse` while Dagster runs. Step 4's single prod instance ends it; until then, a duplicate shows up as a `raw_files` row with the same `path`, `ods_table` and `parser_version`, and fails the ODS asset's `rows_as_loaded` check
- **The image is 1.0 GB** since Dagster, pandas, pyarrow and the BigQuery client joined it. The capture jobs work, but pull a heavy image, and Artifact Registry keeps only one or two releases within the PRD's estimate. Options: a slimmer capture image, or a cleanup policy and accepting it. Decide with the release workflow. dbt makes it heavier: `dbt-bigquery` 1.12 requires `google-cloud-aiplatform`, `google-cloud-dataproc` and `nbformat` (for dbt's Python models, which we don't use), so they come with it
- **No release workflow yet.** Images are built on the laptop and applied with Terraform by hand
- **CI's `warehouse` job runs, hermetic, on pull requests that touch the warehouse:** green in GitHub since 2026-11-18 (49 of 49, 0 bytes read, about a minute). The `e2e` job is green in GitHub since PR #24 (about 6 minutes, 5.5 GB billed a run). Still missing from the plan's CI table: `deploy` (`terraform validate` and `plan`, with the release path). Until then Terraform is checked only on the laptop
- **Dagster on the laptop runs the checked-out branch**, not `main`: `jtf` is installed in editable mode from the working tree, and the dbt project is read from it. A half-finished branch checked out at 08:45 would run in the morning's chain. Since 2026-11-18 development happens in a separate git worktree (`.claude/worktrees/`) and this tree stays on `main`; after a merge, bring it up to `main` with `make dagster-update`, which stops the sensors, waits for running runs, pulls, reloads and starts the sensors again: dbt reads its SQL from disk at every run, but Dagster's asset graph only at a reload, so a run in between mixes the two (it did on 2026-11-18 at 11:02, see the [log](#log)). In prod the image digest pins the code
- **Importing dbt loads a `.env` it finds above the working directory** (dbt 1.12, `dbt/cli/main.py`), without overriding what is already set. Our settings file has that name, so any process that imports dbt from the repository or a worktree inside it, tests included, gets the dev settings and `JTF_RAW_URL`, the prod raw bucket. Nothing under test reads them today: the tests pass fakes and explicit resources, and the rules compile only when asked (`make rules`, CI). But an offline test that resolved a setting would reach dev, or read prod. Options: rename the settings file, or have every test process set each setting before dbt is imported
- **No `make bootstrap`.** The plan (Done when, item 8; step 1), the PRD and `deploy/bootstrap/README.md` say both projects are set up through it, but the Makefile has no such target. Add it with the release path, before phase 4's fork guide needs it
- **`dagster dev` is superseded by `dg dev`** in Dagster 1.13 (a warning in the log). It works; switching can wait for step 4
- **Freshness counts from when Dagster recorded a capture**, not when it landed: while Dagster is down, a source shows late until the sensor catches up
- **MLflow lives on one laptop.** `mlflow.db` and `mlruns/` are local and gitignored: every backtest's metrics, every training's log and every kept model file would go with the machine. The warehouse keeps the predictions, the outcomes and the run records, so results can be scored again, but not the trained files. A durable store (hosted MLflow, or its files in a bucket) comes with the later phases; until then, "a model from last year" is a promise only as long as this disk lasts
- **No second copy of the raw bucket.** The guards cover Terraform, deleted files and a deleted project, but not a billing lapse or a lost account. A daily Storage Transfer copy into another project would (156 MiB so far)
- **Data terms not checked yet.** The test fixtures and notebook outputs republish source data in a public repo. Open-Meteo's data is CC BY 4.0, which needs attribution; TEPCO's and JEPX's terms are still to read. The e2e world adds 4.5 MB of raw files (TEPCO, Open-Meteo, METI) to the repo. Add a data-sources and attribution section with the step-9 README, sooner if the terms require it
- **A reproduce needs its original's commit until images exist.** After any merge, earlier runs reproduce only from a clean checkout of their own commit, not from Dagster's. Runs from before `99f074d` (the ADS rename) can't be reproduced at all: their commit reads the old table names, dropped on 2026-11-19. That loses step 6's what-if and its reproduce; the persistence backtest of 2026-11-17 never had a record. Images, with the release path, end it: a reproduce then runs its original's image
- **A run records the commit checked out when it runs**, not the one Dagster's code location loaded. After a pull without a reload (the skew of 2026-11-18, 11:02; again on 2026-11-19, 09:23, by a `git pull` by hand) a run would record a commit whose Python it didn't run; dbt's SQL would match, since dbt reads it at run time. `make dagster-update` keeps the two together, and since 2026-11-19 reloads even with nothing to pull, but nothing checks it. When it matters: record the commit when the location loads, and refuse a run once the checkout has moved
- **The next-day forecast is published around 18:50 JST and rewritten around 21:50 with the same values** (both days so far; the file's update line says 18:50:12 and 21:50:03 for 16 November, 18:50:16 and 21:50:02 for the 17th), so each capture runs about 10 minutes behind a write. Watch whether one ever misses
- **Cloud Scheduler can start a job twice.** At 22:00 on 2026-11-16 the scheduler made two attempts for `jtf-fetch-tepco-area-forecast-next-day`, 30 seconds apart and both answered, so the job ran twice and stored two identical files. Harmless: a capture seen again adds no version, and ODS keeps both copies by design
- **Dagster on a laptop stops while the laptop sleeps.** On 2026-11-17 the machine suspended at 01:33 and woke at 10:12, so the 08:45 captures were parsed at 10:17 instead of 08:47; on 2026-11-18 it slept from 01:42 until a reboot at 08:59, and `make dagster` had to be restarted by hand. Nothing is lost: capture runs in prod, and the sensor records whatever it hasn't seen when it wakes. Keep the machine awake around 08:45, or accept the delay until step 4 puts Dagster on a VM
- **Every parse rebuilds `dwd_tepco_actuals` and DWS**, not only the actuals' parse: they read the manifest, which every parse writes (JEPX at 11:00, the next-day files at 19:00 and 22:00, capacity at 08:45). A few extra rebuilds a day; the costly one is `dws_weather`, a 611 MB read each time, about 3 GB a day, inside the free tier. `dwd_source_captures` alone won't narrow it: Dagster rebuilds downstream whenever an input materializes, changed or not, and every parse writes the manifest. Narrowing needs Dagster to see that nothing changed (data versions on dbt assets): a spike for step 4, where prod doubles the reads

| Where | What | Handled by |
| --- | --- | --- |
| Dagster | The default automation sensor starts stopped | Declared in code as running |
| Dagster | Eager automation never runs a partition recorded before the asset existed | The first load of a day is by hand (Materialize or a backfill) |
| BigQuery | `ROWS` is a reserved word | The manifest column is `row_count` |

| TEPCO | Pages answer 403 to the WebFetch tool | Fetch with `curl` and a user agent |
| TEPCO | This month's archive zip doesn't exist on the 1st (404) | The daily capture takes yesterday's month and the one before |

| Open-Meteo | Connections from Cloud Run sometimes fail to open | The `PATIENT` retry policy and 3 task retries |
| Open-Meteo | Runs missing from the Single Runs archive answer 400 | Stored once as recorded gaps, with `gap: true` in the sidecar |
| BigQuery | `GENERATE_TIMESTAMP_ARRAY` stops at about a million elements | Days and minutes generated apart, then crossed |
| BigQuery | `MOD` takes no floats | `x - n * floor(x / n)` |
| BigQuery | A CTE named like one of its columns returns the whole row as a struct when selected | Different names for CTEs and columns |
| BigQuery | Float `SUM` isn't deterministic: the order of addition varies from run to run | Sums written out in a fixed order, `(s0 + … + s5) / 6`; capacity figures summed as `NUMERIC` (an incremental and a full build differed by 5 × 10⁻¹⁰ kW on 8 of 297 figures before) |
| BigQuery | Partitions and clustered blocks are pruned only by constants: picking out one file through a subquery or a join read 1,578 MB, more than reading everything (784 MB) | dbt looks the files up first and writes them in (macro `only_files`; notebook 04, section 6.8) |
| dbt-bigquery | An incremental merge reports only the merge's bytes; the read happens in the temporary table it builds first | Costs read from the job history (`INFORMATION_SCHEMA.JOBS_BY_USER`) |
| dbt | A unit test renders `this` and sources as fixtures, so a `run_query` lookup can't run in one; an incremental model's tests must set `is_incremental`, and `this` as a SQL fixture needs no table | `only_files` adds nothing in a unit test; the model filters on the same list in SQL |
| `bq` CLI | Without `--project_id`, a query runs, and is billed, in gcloud's default project, even on fully qualified tables | Pass `--project_id` |
| dbt | A unit test whose expected rows are SQL (`format: sql`) must give every column of the model, not only the ones it checks: dbt selects them all from it | The spine's unit test computes `slot_start` too |
| dbt | Unit tests compare exactly, with no tolerance for floats | A reference seed and a singular test with a tolerance (`dim_sun_slots__matches_spa`) |
| dbt | `dbt-bigquery` 1.12 requires `google-cloud-aiplatform`, `google-cloud-dataproc` and `nbformat` | Accepted; see the image size under [Known issues](#known-issues) |
| uv | Downloads from PyPI time out on a slow line | `UV_HTTP_TIMEOUT=600 uv sync` |
| Dagster | `eager()` on an unpartitioned asset waits until every partition of its partitioned parents exists, so one day with no capture blocks it for good, re-parses included | `rebuild_on_update` for the dbt models, pinned by a test with a never-parsed day |
| Dagster | A table every asset writes and none owns (the manifest) never updates in Dagster's eyes, so nothing downstream of it runs | Each parse that writes it reports a materialization on it |
| Dagster | `materialize` checks partition keys against the real clock | Automation tests use past partitions |
| dagster-dbt | A singular test that reads two models attaches to neither asset | `meta.dagster.ref` names its model |
| Open-Meteo | Previous Runs' lead 0 for the hours just before a fetch changes in a later fetch; leads 1 and 2 don't | Versioned like every source ([notebook 04](../../notebooks/04_ods_to_dwd.ipynb), section 3.4) |
| healthchecks.io | A check that has gone down stays down until its next ping, even after its schedule changes | Pause it: the next ping resumes it |
| Dagster | A model that reads the manifest rebuilt after a parse's first step, while later steps still ran: the spine moved to a new target day ahead of the DWD it is joined with, and `dws_solar_features__d2_complete` failed until the next rebuild a minute later | The manifest is declared downstream of every ODS asset, and `rebuild_on_update` waits while an input's own inputs are being built; a test reproduces the race and fails without the fix |
| Dagster | Holding a model back while its inputs, or their inputs, are being built is two levels, and the graph is deeper: a tick inside a parse run let three readers of the spine build before the spine, which sat one step further from the parse. Dagster has no condition for "any ancestor in progress" | The guard is nested as deep as the graph (`LEVELS`, 12, where the furthest model is 8 steps from a parse); a test fails when the graph outgrows it, and another replays the tick. A tick's evaluation costs about 1.5 s for it, against 0.05 s |
| dagster-dbt | dbt reads the project from disk at every run, while Dagster's asset graph and selection come from the last code-location load. A pull between the two ran the new SQL on the old graph: the spine read `dwd_source_captures`, which the old graph had no asset for, so nothing had rebuilt it since the night before, and the spine fell back a day; a unit test naming the new model failed to compile | `make dagster-update`: no run between the pull and the reload; and a check that the spine reaches the day after the newest capture in ODS, so a spine built from stale captures fails |
| dbt | Partial parsing kept a unit test renamed in a YAML file under its old name too, with its old inputs, so it failed to compile in every build that selected its model. It takes both changes in one parse: the rename and any edit to a sources file (reproduced on a copy of `beec316` pulled to `e7178c7`, and on a three-file project). A fresh parse, as in CI, never sees it | `partial_parse: false` in `dbt_project.yml`, about a second per parse; `rules/test_parse.py` |
| dbt-bigquery | `--empty` compiles each `ref()` and `source()` to `(select * from … where false limit 0)`, so a rule over that SQL sees every table behind a wrapper of its own | The SQL rules read a separate `dbt compile`, with the build's target and vars |
| dbt | `dbt compile` needs BigQuery credentials even with `--no-introspect` and `--no-populate-cache`, though it reads no data | The rules over compiled SQL run in CI's `warehouse` job and `make rules`; `make test` skips them |
| dbt | Importing `dbt.cli.main` loads a `.env` found by searching upward from the working directory: tests that set no settings found the dev ones | The rules compile only when asked; the rest in [Known issues](#known-issues) |
| dbt and Dagster | dbt names a generic test from its arguments with the operators dropped, so `basis = 'rule' or known_at = first_seen` and `basis != 'rule' or known_at <= first_seen` on one model got one name; Dagster keys a check by asset and name and kept one of the two, so one result would have hidden the other | Such tests are named in their YAML; `test_every_dbt_test_is_a_check_of_its_own` fails if two share a name, or if Dagster's checks don't number dbt's tests |
| BigQuery | A partition's `last_modified_time` moved exactly where an `UPDATE`, a `DELETE` or a load touched it, and not for a new column; but its docs warn that *"Modifications that involve record deletions might not be reflected"* | The fingerprint check screens partitions by their row count too ([notebook 07](../../notebooks/07_ods_fingerprints.ipynb)) |
| BigQuery | `BIT_XOR` of row hashes cancels a file loaded twice to exactly 0 | The fingerprint sums the hashes as `BIGNUMERIC` |
| BigQuery | A query of `INFORMATION_SCHEMA.PARTITIONS` bills about 10 MB however little it reads | Accepted: the checks after every load cost about 300 MB a day |
| Python | A break made to watch a test fail, restored within the same second and at the same size (lines only reordered), kept running: the `.pyc` checks the source's mtime to the second and its size, so the compiled break stayed in use | `PYTHONDONTWRITEBYTECODE=1` when breaking code by script |
