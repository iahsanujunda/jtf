# orchestration

Dagster definitions. Assets are thin wrappers over `jtf` functions: no logic lives here that can't be tested without Dagster.

| Piece | Phase |
| --- | --- |
| External `raw` assets, one per source, and the raw-bucket sensor that records each landed file | 1 |
| Freshness checks per capture source (08:45 sources by 09:00, `jepx_spot` by 11:30, next-day sources by 22:30) | 1 |
| Partitions: extraction day for raw and ODS; decision date from 2024-02-16 for DWS and predictions (target day 2024-02-17, the first with full MSM radiation) | 1 |
| ODS assets with declarative automation on new raw records, and two checks after each load: every parsed file passes its per-file checks (`files_pass_checks`), and every file's rows still match the fingerprint recorded at their load (`rows_as_loaded`, [parse README](../parse/README.md)) | 1 |
| dbt assets through `dagster-dbt`; dbt tests as asset checks; single-run backfill policy for DWS | 1 |
| Backtest, train and replay jobs with run config (`mode`, `T` range, `fault`) | 1 |
| Heartbeat schedule pinging the healthchecks.io check `jtf-dagster` every 15 minutes; run-failure sensor sending failed runs to its `/fail` | 1 |
| Daily prediction schedule at 09:05 JST; evaluation sensor on new actuals | 2 |
| Retrain job, shadow runs, export job | 2–3 |
| Run-failure sensor that starts AI triage | 5 |

Every asset carries a code version, so a release that changes one marks its partitions out of date. Every run is tagged with its image digest.

**dbt** ([dbt.py](dbt.py)): every model and seed in `warehouse/dbt` is an asset keyed `<layer>/<name>` (`dwd/dwd_tepco_actuals`), grouped by layer, and in ADS, which serves applications, by application, its name's second word (`ads_ml`; `group_of`), with dbt's data tests as its checks; a test that reads two models names its own in `meta.dagster.ref`. A run is `dbt build` of the selection. dbt's sources resolve to the ODS assets, so lineage runs from each raw file to every model. The manifest, `ods/raw_files`, is written by every ODS parse and owned by none: a parse that writes it reports a materialization on it, so the models that read it rebuild, and it is declared downstream of every ODS asset. Models rebuild when any input updates (`rebuild_on_update`), not with `eager()`: under the day-partitioned ODS assets, `eager()` waits for every day to be parsed, so one failed capture would stop the warehouse for good. Nor do they start while anything upstream of them is being built, however far: a parse reports the manifest from its first step, so without that a model would rebuild mid-parse, ahead of what it is joined with (it happened on 2026-11-17, and again on 2026-11-19 one step further up than the guard then looked). Dagster has no condition for "any ancestor in progress", so the guard is nested `LEVELS` deep, and a test fails when the graph outgrows it. All of it is tested with stand-ins in `jtf/tests/test_orchestration.py`. Seeds change only with code and are materialized by hand. `dwd_capacity_area_files` is incremental and runs like the rest; a change to its columns needs one `--full-refresh` build by hand (`make dbt ARGS="build --select dwd_capacity_area_files --full-refresh"`), and until then its runs fail rather than merge rows of two shapes. `dagster dev` re-parses the dbt project on every load; anywhere else the manifest is parsed once if missing. Every parse is a full one (`partial_parse: false` in `dbt_project.yml`): a partial parse once kept a renamed unit test under its old name too, and the stale copy failed every build of its model.

**Runs** ([ml.py](ml.py), [jtf.ml.replay](../ml/replay.py)), made by hand through two jobs. `replay` materializes `ads/ads_ml_prediction_solar` and `ads/ads_ml_outcome_solar`: a what-if over target days by default (config `first_target_day`, `last_target_day`), or `mode: reproduce` with `reproduces`, an earlier run's ID. `backtest` adds `ml/solar_backtest_metrics`: the test months (config `first_test_month`, `last_test_month`, by default March 2025 to the newest month with every slot labelled), its metrics per fold in MLflow with its fidelity counts. Every run appends its predictions under the Dagster run's ID and its record to `ads_ml_runs`. The predictions asset is keyed as dbt's source for that table, so it is one node with it and `ads/ads_ml_outcome_solar` (dbt) rebuilds from it; it is grouped with it in `ads_ml`, and the metrics, which live in MLflow, in `ml`. Both read and write dbt's datasets through the `datasets` resource (`<prefix>_<layer>`).

**Locally:** `make dagster` serves the UI on http://localhost:3000, keeps Dagster's state in `.dagster/` and reads settings from a gitignored `.env` at the repo root (names in [deploy/contract](../../../../deploy/contract/settings.example.env)): `JTF_RAW_URL`, the raw bucket; `JTF_BIGQUERY_PROJECT`, the project of the warehouse that is kept; dbt's `JTF_BIGQUERY_LOCATION` and `JTF_DBT_DATASET_PREFIX`; and `JTF_ENV`. Before Dagster starts, `make dagster` refuses settings that name prod unless the checkout is `main` with nothing uncommitted, writes Dagster's own settings from [deploy/dagster](../../../../deploy/dagster/README.md), and makes the tables Python writes as the code has them (`jtf warehouse ensure`). Both sensors, `raw_bucket_sensor` and `automation`, start running. A day recorded before its ODS asset existed is loaded by hand (Materialize, pick the partition); from then on, a newly recorded capture starts the parse of its day on its own. Dagster need not run all the time: the ODS assets' condition (`PARSE_WHEN_LANDED` in [ods.py](ods.py)) is Dagster's `eager()` with its window widened from the newest day to the last six weeks, so the days recorded after time off are all parsed, not only the newest. The checkout Dagster runs from is brought up to `main` only with `make dagster-update` ([update.py](update.py)): it stops both sensors, waits for the running runs, pulls, runs the new code's `jtf warehouse ensure`, reloads the code location and starts the sensors again, so no run reads the new SQL with the old asset graph. It refuses a checkout without `.dagster/`, off `main` or with uncommitted changes, and a pull that changes dependencies, which needs `make setup` and a restart instead; if the tables can't be made or the new code fails to load, the sensors stay stopped.
